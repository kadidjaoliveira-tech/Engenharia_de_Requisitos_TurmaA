# Unidade 5 - Estrutura de Pitch Deck para o Produto

Este documento apresenta uma estrutura de pitch deck para a apresentação de um produto em disciplina de Engenharia de Requisitos. Ele reúne os principais elementos esperados em uma apresentação: Lean Canvas, especificação de caso de uso, diagrama de classes e estrutura da equipe ágil.

## 1. Slide de abertura
- Nome do produto
- Proposta de valor em uma frase
- Identidade visual ou logo
- Integrantes da equipe

Exemplo:
> "[Nome do Produto] ajuda [público-alvo] a [resolver problema] por meio de [solução]."

## 2. Problema e oportunidade
- Descreva o problema identificado.
- Explique quem é afetado.
- Apresente a dor atual e as consequências.
- Mostre por que a solução é relevante.

### Exemplos de tópicos
- Falta de praticidade
- Processos manuais e ineficientes
- Dificuldade de organização
- Baixa visibilidade de informações

## 3. Solução proposta
- Descreva a solução de forma clara e objetiva.
- Explique como ela ajuda o usuário.
- Destaque o diferencial em relação ao que existe hoje.

## 4. Lean Canvas
O Lean Canvas organiza a ideia em blocos essenciais.

### Estrutura sugerida
- Problema
- Segmentos de clientes
- Proposta de valor
- Solução
- Canais de distribuição
- Fontes de receita
- Estrutura de custos
- Métricas principais
- Vantagem injusta

### Exemplo de preenchimento
- Problema: usuários perdem tempo em tarefas repetitivas
- Clientes: estudantes, pequenas empresas, gestores
- Valor: agilidade, organização e maior controle
- Solução: plataforma digital com gestão centralizada
- Canais: web, redes sociais, apresentações e parcerias
- Receita: assinatura, mensalidade, valor por uso
- Custos: desenvolvimento, hospedagem, manutenção
- Métricas: usuários ativos, tempo de uso, taxa de retenção
- Vantagem: experiência intuitiva e foco no usuário

## 5. Requisitos do produto
### Requisitos funcionais
São as funcionalidades que o sistema deve realizar.

Exemplos:
- O sistema deve permitir cadastro de usuários.
- O sistema deve registrar informações importantes.
- O sistema deve disponibilizar relatórios ou consultas.
- O sistema deve permitir autenticação segura.

### Requisitos não funcionais
São critérios de qualidade do sistema.

Exemplos:
- Tempo de resposta inferior a 2 segundos.
- Interface intuitiva e acessível.
- Segurança na autenticação e proteção de dados.
- Disponibilidade do sistema em horário comercial.

## 6. Especificação de caso de uso
A especificação de caso de uso descreve a interação entre usuário e sistema.

### Estrutura
- Nome do caso de uso
- Ator principal
- Objetivo
- Pré-condições
- Gatilho
- Fluxo principal
- Fluxos alternativos
- Pós-condições

### Exemplo
- Caso de uso: Realizar cadastro
- Ator: Usuário
- Objetivo: Criar uma conta no sistema
- Pré-condições: usuário acessa a página inicial
- Gatilho: clique em "Cadastrar"
- Fluxo principal:
  1. O usuário informa dados pessoais
  2. O sistema valida os dados
  3. O sistema cria a conta
  4. O sistema exibe mensagem de sucesso
- Fluxos alternativos:
  - dados inválidos
  - e-mail já cadastrado
  - falha de conexão
- Pós-condições: usuário autenticado e conta criada

## 7. Diagrama de classes
O diagrama de classes representa os elementos principais do sistema e seus relacionamentos.

### Classes sugeridas
- Usuário
- Produto
- Pedido
- Serviço
- Categoria
- Administrador
- Relatório

### Exemplos de atributos
- Usuário: id, nome, e-mail, senha
- Produto: id, nome, descrição, preço
- Pedido: id, data, status, total

### Exemplos de relacionamentos
- Usuário realiza Pedido
- Pedido contém Produtos
- Administrador gerencia Produtos
- Produto pertence a Categoria

## 8. Estrutura da equipe ágil
A equipe ágil deve ter papéis bem definidos para facilitar o desenvolvimento.

### Papéis sugeridos
- Product Owner: define prioridades e representa o cliente
- Scrum Master / Facilitador: organiza o processo e remove impedimentos
- Analista de requisitos: coleta e documenta necessidades
- Desenvolvedores: implementam as funcionalidades
- Testadores: validam qualidade e correção
- Designer/UX: organiza a experiência do usuário

### Exemplo de organização
- Product Owner: define o backlog
- Scrum Master: conduz reuniões e facilita o trabalho em equipe
- Time de desenvolvimento: cria, integra e entrega funcionalidade
- Analista: valida requisitos e documentação

## 9. Planejamento do MVP
O MVP (Minimum Viable Product) deve conter apenas o que é essencial para validar a ideia.

### Critérios para MVP
- Resolver o problema principal
- Ser testável com o usuário real
- Ter baixa complexidade de desenvolvimento
- Permitir coleta de feedback

### Exemplo de MVP
- Cadastro de usuário
- Login
- Registro de dados principais
- Visualização de informações essenciais
- Funcionalidade central do produto

## 10. Conclusão do pitch
A apresentação final deve responder:
- Qual é o problema?
- Para quem é a solução?
- Como ela funciona?
- Por que é importante?
- Como a equipe vai desenvolver e validar?

Uma boa apresentação deve ser clara, objetiva e conectada aos requisitos levantados durante o processo de engenharia de requisitos.

## 11. Checklist final para apresentação
- Problema bem definido
- Público-alvo identificado
- Requisitos funcionais descritos
- Requisitos não funcionais definidos
- Caso de uso especificado
- Diagrama de classes apresentado
- Estrutura da equipe ágil explicada
- Lean Canvas preenchido
- MVP apresentado de forma clara
- Mensagem final objetiva e convincente
